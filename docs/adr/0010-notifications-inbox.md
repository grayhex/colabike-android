# ADR 0010. Центр уведомлений ColaBike

Статус: принято в рамках [issue #8](https://github.com/grayhex/colabike-android/issues/8), 04.10.2026, первый из двух PR (читаемый inbox отдельным первым PR разрешён задачей); второй — мессенджер на Stream Chat. Дополнен 04.10.2026 разделом «Прочитано, фильтры и типизированная цель» ([issue #30](https://github.com/grayhex/colabike-android/issues/30), контракт [cola#341](https://github.com/grayhex/cola/issues/341)); push — [ADR 0015](0015-push-notifications.md). Опирается на [ADR 0007](0007-comments.md) (обсуждение с `focus`) и [ADR 0003](0003-account-guest-and-web-flows.md) (роутер ссылок).

## Что решено

- **Читается только то, что есть в API v1:** `GET /me/notifications` (страницы по курсору, новые сверху) и `GET /me/notifications/count`. Контракт проверен свежим снимком (`updateApiContract`, diff пуст): **операции «пометить прочитанным» в API нет**. Это backend gap, он записан здесь и в `docs/screen-api-mapping.md`.
- **Без фиктивного «прочитано».** Приложение ничего не помечает и не обнуляет число у колокольчика локально: открытие inbox не меняет серверный счётчик. Экран один раз и прямо говорит об этом («Прочитанными уведомления отмечаются на сайте… число у колокольчика не уменьшается»). Состояние «не прочитано» берётся из `readAt` и показывается точкой и словом «Новое» в озвучке, а не одним цветом.
- **Колокольчик в шапке верхних экранов** (Велосипеды, Лента, Покатушки, Профиль) показывает серверное число. Число спрашивается при возвращении в приложение и при переходах по приложению, не чаще раза в полминуты; сбой запроса оставляет прежнее число (ошибка счётчика — не экран ошибки). `capped` (сервер считает до 100) никогда не выдаётся за точное число: показывается «99+», озвучка — «непрочитанных не меньше ста». Число от 1 до 99 точное. У гостя нет ни колокольчика, ни запросов. Число не смешивается с непрочитанными сообщениями чата (отдельный счётчик во втором PR).
- **Открытый набор видов.** `type` уведомления и `target.type` — открытые строки. Известные виды (`follow`, `like`, `comment`, `reply` и их `ride_*`/`journal_*`/`article_*`, `component_reply`, `market_expiring`, `session_reuse`, `bike_week`) получают свой заголовок; неизвестный получает общий вид «Новое событие» с названием объекта и по-прежнему открывается.
- **Переход идёт по типизированному `target`, а не разбором пути:** `bike`, `ride`, `journal` открывают свой экран, `profile` — страницу человека, `account` с `session_reuse` — «Устройства». Для уведомления о комментарии (`comment`, `reply`, `*_comment`, `*_reply`) путь несёт якорь комментария: берётся первый UUID фрагмента (как бы ни назывался якорь), и открывается обсуждение на этом комментарии (сервер возвращает ветку и цепочку, [ADR 0007](0007-comments.md)). Формат якоря в контракте не описан, поэтому читается терпимо; нет якоря — открывается сам объект. Всё остальное (`market`, `article`, `component`, `bike-week`, неизвестные типы) открывается на сайте по пути из `target.path`, и только если это путь на хосте сайта (`SiteLinks.pageFromPath`: один `/` в начале, без управляющих символов и `\`, тот же `https`-хост и порт); иначе строка не нажимается.
- **Удалённый или закрытый объект** открывается в обычное «не найдено» своего экрана, прежнего приватного содержимого нет (сервер сам не показывает уведомления о том, что получатель уже не вправе видеть).
- **Роутер ссылок обновлён:** адреса `/j/<uuid>` и `/r/<uuid>` теперь ведут на экраны журнала и покатушки, а не на сайт (экраны появились в #6 и #7).
- **Чтение inbox на сервере** создаёт напоминание о конце срока объявления (раз за срок), как и на сайте; приложение не делает лишних чтений: страницы по курсору, обновление жестом.

## Прочитано, фильтры и типизированная цель (issue #30, контракт cola#341)

Пункты выше про «пометки нет» и «число не уменьшается» относились к API до cola#341; ниже то, что заменило их.

- **Контракт** — снимок `api/openapi.json` собран из `main` бэкенда после merge cola PR #344 (`updateApiContract -PcontractUrl=…`), общие примеры бэкенда (`targets.json`, `read.json`, `payload.json`, `preferences.json`) лежат в `core/network/src/test/resources/contracts/notifications/v1` и закреплены коммитом `316d604` из `SOURCE.txt`; тест `NotificationsRepositoryTest` читает ими каждое уведомление и каждый ответ на «прочитано». До выкладки бэкенда `checkApiContractDrift` красный, а список уведомлений на production не читается: `category` в ответе обязательное поле.
- **Что значит «прочитано».** Сервер хранит один факт. Загрузка списка, показ и смахивание ничего не помечают; прочитанным делает приложение, когда человек открыл уведомление, нажал «Отметить прочитанным» на карточке или «Прочитать все». Карточка показывается прочитанной только после ответа сервера: отказ оставляет её новой (без локальных догадок), для кнопки и «Прочитать все» отказ назван на экране (`liveRegion`), при открытии отметка повторится при следующем открытии. Число у колокольчика берётся из ответа на пометку (`unread`, `capped`), а не вычитается на месте.
- **«Прочитать все»** идёт до `watermark` первой страницы списка (позиция самого нового уведомления, которое человек мог видеть): пришедшее позже остаётся непрочитанным. Отметка непрозрачна, возвращается как есть и действует только для аккаунта, которому выдана; отметка, которой сервер уже не знает (чужая, уведомление, на которое она указывала, удалено), даёт 400: приложение берёт свежую вместе с обновлённым списком и просит нажать ещё раз. вторая страница, пришедшая позже, её не сдвигает. Выбрана категория — идёт только она. Запрос повторяется, пока ответ «заполнен» (10 000 за раз), не больше пяти раз; «`unread` не ноль» поводом повторять не считается, потому что пришедшее позже остаётся непрочитанным по замыслу.
- **Фильтры.** «Непрочитанные» (`unread=1`) и одна категория (`rides`, `discussions`, `market`, `reactions`, `site`) вместе; смена фильтра начинает список заново и отменяет прежний запрос. Неизвестная категория — «другое»: показывается в общем списке и своего фильтра не получает. Пустой ответ под фильтром называет причину.
- **Типизированная цель.** Комментарий берётся из `target.commentId`, якорь пути читается только у старого сервера. Дата выезда (`occurrenceAt`) и версия договорённостей (`agreementRevision`) приходят в модель и показываются в тексте уведомлений о покатушке (приглашение, изменение, отмена, ответ, напоминание), но отдельного экрана «дата покатушки» в приложении нет: открывается сама покатушка. Неизвестный вид цели по-прежнему открывается на сайте по `path` (только путь на хосте сайта).
- **Выбранные** (`POST /me/notifications/read`) есть в репозитории (по сто в запросе), экранов выбора пока нет: его первый потребитель — синхронизация шторки в push-срезе.
- **Не сделано здесь:** группировка по смыслу (нужна модель дедупликации сервера, N1.2), настройки каналов и согласие на push ([ADR 0016](0016-notification-settings.md)), push и системные уведомления ([ADR 0015](0015-push-notifications.md)).

## Чего нет

- Push-уведомлений (не входят в этот PR и не подключаются автоматически: ни FCM, ни GMS; канал — RuStore, [ADR 0015](0015-push-notifications.md)) и группировки по смыслу.
- Реальных тестовых аккаунтов в живом smoke: он читает только списки и страницы; inbox проверяется на фейках и MockWebServer.
